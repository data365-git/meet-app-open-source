# data365 vs Loom — Honest Product Comparison

> Scope: data365 = this repo (`apps/web`, a Cap fork), as the code actually exists today — not roadmap, not marketing. Loom = general knowledge of Loom as a product (training-data knowledge, not live-verified). This is a decision document for the owner, not marketing copy.
>
> Evidence standard: every data365 claim below is backed by a file path I read. Where I could not confirm something in code, it is marked **unverified** rather than guessed.

---

## TL;DR verdict

- **data365 wins decisively on AI depth for non-English markets**: RAG chat-with-video with clickable timestamp citations, speaker diarization, an org/per-video AI output language (Uzbek/Russian/English), and an on-demand multi-language re-generation flow (analysis + refined transcript + captions) that Loom does not offer at all.
- **data365 wins on data ownership**: real self-host path (Docker/Railway, bring-your-own S3-compatible storage, bring-your-own Gemini/Anthropic/OpenAI key) — Loom is SaaS-only, no self-host option exists.
- **data365 meaningfully lags on polish, breadth, and trust signals**: no mobile apps, no third-party integrations (Slack/Jira/Notion/Zapier — none found in code), no SSO (`get-organization-sso-data.ts` literally throws "SSO is not configured on this instance"), no SOC2-style compliance posture, and viewer analytics is shallow (view count + comments + reactions, no per-viewer watch-% or engagement curve).
- **data365 has real but rougher core recording/editing**: web recorder + Chrome extension recording both work and are sophisticated (codec fallback chains, progressive upload, crash-recovery spooling); there is **no desktop app** in this repo despite the DB schema still carrying desktop source types; video trim/cut exists server-side (`/video/edit` on the media server) but there's no evidence of a polished in-browser trim UI comparable to Loom's editor.
- **Who it's for**: data365 is the right choice for an Uzbek/Russian-speaking org (or a security-conscious org) that wants AI-native meeting/video understanding and control over its data, and is willing to accept a less mature ecosystem (no mobile, no integrations, no SSO) in exchange. Loom remains the better choice for English-first teams that need broad tool integration, mobile recording, and enterprise compliance out of the box.

## Where we genuinely win

1. **Chat-with-video (RAG over transcript)** — `apps/web/app/api/video/ai/chat/route.ts`. Streamed, timestamp-cited, synthesizes across the whole recording for broad questions. No Loom equivalent.
2. **Uzbek/Russian quality, not just translation** — AI *generates* analysis natively in the target language (not machine-translated after the fact), with explicit anti-transliteration guardrails in the prompt. This is a deliberate quality investment, not a checkbox feature.
3. **Speaker diarization** in the transcript and chat context (`<v Speaker N>` WebVTT tags), letting summaries and chat answers reference who said what.
4. **Refined transcript** — a distinct, readable paragraph-form rewrite of the meeting separate from the raw verbatim transcript, organized by chapter.
5. **On-demand multi-language re-generation** — a viewer (with permission) can request the AI analysis, refined transcript, and (per `docs/STATE.md` ИSH 3 planning notes) eventually captions in a different language, with caching so repeat switches are instant. This is actively being extended (per-video language picker is in-progress per STATE.md, not yet fully shipped — see gaps below).
6. **Self-host / data ownership** — genuinely deployable on infrastructure the owner controls, with bring-your-own storage and bring-your-own AI key. For an org with data-sovereignty concerns (e.g., Uzbekistan-based, regulatory, or just cost-conscious), this is structural, not cosmetic.

## Where we lag / gaps to close

Said plainly, not softened:

1. **No mobile apps.** Recording and viewing are web/extension only. If users expect to record or watch from a phone app, this is a hard gap.
2. **No third-party integrations.** No Slack, Jira, Notion, Zapier, webhooks-for-third-parties, or anything like it was found in the codebase. Loom's integration breadth is a major adoption driver for teams already living in those tools; data365 has nothing here today.
3. **No SSO.** The SSO action is a literal stub that throws an error. Any enterprise prospect that requires SAML/OIDC is currently a hard no.
4. **Shallow analytics.** View count + comments + reactions only. No per-viewer identity, no % watched, no drop-off curve — explicitly tracked as unbuilt in `ROADMAP.md` (item C4).
5. **No desktop app**, despite the database schema still carrying desktop-recording source types from the upstream Cap project — this looks like a feature that existed upstream and was not carried into this fork/deployment.
6. **Editing is thin.** Trim/cut exists at the media-server API level and there's a pre-upload WASM trimmer, but there's no evidence of Loom-grade in-browser stitch/multi-clip editing, filler-word removal, or transcript-based editing (these are explicitly listed as not-yet-built "Loom big features" in `ROADMAP.md` C1–C3).
7. **Task checkboxes don't persist** — `TasksPanel.tsx:107` has an open TODO for this per `docs/STATE.md`; AI-extracted action items can be viewed but checking them off doesn't currently save.
8. **No compliance posture.** No SOC2/GDPR-specific tooling or documentation found. Not necessarily wrong for the current stage, but it will surface as a blocker the moment this is sold into a regulated or enterprise buyer.
9. **No cross-library/semantic search.** Search works within a single video's transcript or by title across the library — not "find the meeting where we discussed X" across all recordings.
10. **Recent bug-fix history (per `docs/STATE.md`) shows the AI pipeline has been fragile** — multiple recent fixes for AI generation getting silently truncated/swallowed, captions failing to render due to non-standard VTT, and UI state not refreshing after AI completes. These are being actively fixed, but it signals the AI feature surface, while differentiated, has had real production reliability issues that a head-to-head Loom comparison should not paper over.
11. **Chat-with-video access control needs a second look.** `apps/web/app/api/video/ai/chat/route.ts` does gate access through `VideosPolicy.canView` (so it respects public/private and password state), and has a per-`videoId+IP` in-process rate limiter (20 req/min). However, that rate limiter is an in-memory `Map` that resets on every deploy/restart and isn't shared across server instances — on a multi-instance deployment it under-protects. Since every chat call spends the *video owner's* Gemini key (or the instance's shared key), a public+unlisted video with many viewers chatting concurrently could run up real AI cost beyond what the per-org/per-video budget caps (`ai-cost-guard.ts`) catch in time. Not a broken-access bug, but a cost-abuse surface worth hardening before this is opened to untrusted public viewers at scale.

## Strategic takeaways

1. **Lean hard into the AI-native, multi-language story** — it's the one area where data365 isn't just "catching up to Loom," it's doing something Loom doesn't do at all. This is the actual wedge, especially for Uzbek/Russian-speaking markets Loom doesn't serve well.
2. **Don't pretend this is a SaaS competitor on breadth** — no mobile, no integrations, no SSO means data365 is not yet a like-for-like Loom replacement for an English-first, integration-heavy team. Position it explicitly as "AI-native, self-hosted, regional" rather than "Loom but better."
3. **Closing the analytics gap is probably higher leverage than it looks** — basic view/comment counts undersell a product that already has rich AI metadata (chapters, speakers, topics) sitting in the database. A "who watched, how far, on which topic" view could be built largely from data already captured.
4. **Finish what's already half-built before adding new scope** — per-video language picker, task-checkbox persistence, and AI pipeline reliability (truncation/caption parsing bugs from `docs/STATE.md`) are in-flight or recently-patched. Shipping these solidly is cheaper and higher-value right now than starting SSO or integrations.
5. **SSO and at least one integration (Slack notification on share, at minimum) are the most likely blockers if this is ever pitched to a larger org** — worth scoping as a deliberate future project once the core AI/reliability work is stable, not before.
