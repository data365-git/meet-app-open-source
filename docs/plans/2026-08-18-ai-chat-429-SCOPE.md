# AI chat dies with 429 on any video whose index is not built — SCOPE / METRIC / DIRECTION

_Owner, 2026-08-18: "ai chat ishlamayapti pullik kalitga ulab qoyy", then "open router kalitini ulab qoyy ai chatga ham"._
_Both instructions rest on a premise the evidence below falsifies: there is no separate paid key to connect, and OpenRouter cannot serve the step that is failing. The half he asked for is already done._

## SCOPE — what is broken, reproducible by someone else

`POST https://data365.duckdns.org/api/video/ai/chat` with
`{"videoId":"2e466nedt9f8kgp","messages":[{"role":"user","content":"…"}]}`
— no auth needed, the video is public — streams exactly one frame:

```
data: {"error":"Gemini batchEmbedContents failed: 429 … \"status\": \"RESOURCE_EXHAUSTED\" …"}
data: [DONE]
```

The same request against `dmz6gk93rjnb9kn` returns a correct streamed Uzbek answer. The
difference is not the key and not the account: `dmz6gk93rjnb9kn` **already has its transcript
index built**, so it only has to embed the one-sentence question, while `2e466nedt9f8kgp` has to
build the whole index first — `ensureTranscriptIndex` → `embedChunksWithUsage` →
`batchEmbedContents` with **`BATCH_SIZE = 100` documents in a single request**
(`lib/gemini-embed.ts:3,32-37`).

This is what the owner sees as "AI chat ishlamayapti": it works on old videos and fails on new ones.

Nginx confirms it is not a one-off — his Android client got two identical 735-byte responses at
15:05:59 and 15:06:42 on that video, both HTTP 200 (the error rides *inside* a 200 SSE stream, which
is also why nothing appears in the app's ERROR log).

**It is a per-minute limit, not an exhausted daily quota.** A single `embedContent` with the very
same key, issued from inside the running container minutes after the failure, returns **HTTP 200**.
So the account is not dead; one oversized request is.

### Four facts that kill the "just connect the paid key" fix

1. **There is no paid key.** Inside the container, `GEMINI_API_KEY === GEMINI_API_KEY_FREE` is
   **true** — the "paid" slot holds the same free key.
2. **No user has a personal key** — `SELECT LENGTH(geminiApiKey) FROM users` is NULL for all three
   rows, so `owner?.geminiApiKey` never applies and the route already falls through to
   `getPaidGeminiKey()`.
3. **OpenRouter cannot do this step.** `POST /api/v1/embeddings` → `404 {"error":{"message":"No
   endpoints available matching your guardrail restrictions and data policy"}}`, and its model list
   holds **413 models, of which 0 are embedding models**. Embeddings have to stay on Google.
4. **OpenRouter is already wired into the chat** — `app/api/video/ai/chat/route.ts:467-472` picks
   `getOpenRouterKey()` for the answer-writing half and parses OpenRouter's stream format
   (`:564,598`). Its key is live and funded ($2.16 used, no cap). The half the owner asked for is
   done; the half that is broken is the half OpenRouter cannot serve.

### Why the existing retry does not save it

`embedChunksWithUsage` already wraps each batch in `withGeminiRetry`, which does retry on 429
(`lib/gemini-retry.ts:2,42`) with exponential backoff — but the delay is capped at **8 seconds**
(`:52`) over a small attempt budget. A per-minute token limit outlasts that window, so every attempt
burns against the same exhausted minute and the whole call fails. The retry is present but too
impatient, and the request it is retrying is too big.

## METRIC — the number that says "fixed"

**M1 (the live gate, runnable from this machine, no login needed):** `POST /api/video/ai/chat`
against a video with **no existing index** returns streamed `{"token":…}` frames and **zero**
`{"error":…}` frames. Pass/fail by `curl | grep -c '"error"'` = 0 — not a judgement.
Baseline today: fails on the first attempt, deterministically, on `2e466nedt9f8kgp`.

**Blast radius, counted on prod 2026-08-18:** of **24** non-deleted videos with
`transcriptionStatus = COMPLETE`, only **8** have rows in `transcript_chunks` — so **16 of 24 (67%)
fail AI chat right now**, every one of them on this same 429. That is the real scale of "ai chat
ishlamayapti": not one video, two thirds of the library. Post-fix, asking a question on any of those
16 must answer.

**M2 (unit, pre-deploy):** against a stubbed transport that rejects any request carrying more than
N documents or arriving sooner than the pacing interval, indexing a transcript of 500 chunks
completes with zero surfaced errors, and a 429 with a `retryDelay` hint is honoured rather than
retried after the hard-coded 8s cap. Mutation-checked.

## DIRECTION — one change → measure → keep or discard

1. Shrink the request: `BATCH_SIZE = 100` documents in one call is the proximate cause. Cut it and
   pace successive batches.
2. Make the backoff patient enough for a per-minute window, and honour the `RetryInfo` /
   `retryDelay` the 429 body carries instead of the 8s ceiling.
3. Keep partial progress, so a retry of a long transcript does not re-embed what already succeeded.
4. Re-run M1 against `2e466nedt9f8kgp`. Keep if it answers; discard if it still 429s.

Deliberately NOT in scope: moving embeddings to another provider (fact 3), and buying Gemini
billing. Billing stays a real option for headroom — it would raise the ceiling rather than pace
below it — but it needs the owner's Google account and money, and this fix needs neither.

## Blast radius

- `embedChunksWithUsage` is shared: the chat's question-embedding and the index build both call it.
  Slower pacing must not add seconds to the one-sentence question path — pace per batch, not per call.
- `withGeminiRetry` is used by `lib/gemini-batch-transcribe.ts:286,314` too. Changing its ceiling
  changes transcription's retry behaviour as well; if the patience is raised, raise it where the
  embed path calls it, not globally, unless transcription is checked in the same change.
- The cost guard (`withCostGuard`) wraps the embed call — more, smaller requests must not be recorded
  as more billable operations than before.
