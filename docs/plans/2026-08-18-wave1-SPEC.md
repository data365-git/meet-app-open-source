# Wave 1 SPEC — stop the two-hour wait (data365, 2026-08-18)

Reviewed plan; blind review returned SHIP WITH CHANGES. This wave carries ONLY the changes that remove the wait. Progress UI, re-press toast and the stranded-upload rescue are wave 2 — do not build them here.

## SCOPE
Every long upload runs `optimizeRemoteVideoToMp4` (`workflows/process-video.ts:113`) before transcription is allowed to start. That call has no options, so `lib/video-convert.ts` applies `DEFAULT_COPY_TIMEOUT_MS = 10 min` (`:20`) and then, from a **bare catch** at `:403`, `DEFAULT_COMPRESS_TIMEOUT_MS = 45 min` (`:23`). A 2-hour upload times out of both, produces nothing, and only then does transcription begin — measured 2 h 03 m of dead time on prod, against 10 minutes for the transcription itself. In the running container the optimization pass has succeeded **0** times and failed **3**.

## METRIC
1. Time from `multipart/complete` to `processingStartedAt` (`lib/transcribe.ts:311`) for a ≥60-min upload: **< 3 minutes** (today: up to 2 h). Read both from the DB after a real upload.
2. `SUM(transcriptionStatus='COMPLETE')/COUNT(*)` over `videos` created in the last 30 days: **≥95%** (baseline 23/32 = 72%).
3. A video deleted mid-run must stop within one chunk and must NOT reach COMPLETE.

## DIRECTION
One change → measure → keep or discard. The three changes below are ordered; each must be independently RED-verified.

---

## CHANGE 1 — a timeout must not buy a 45-minute re-encode
`lib/video-convert.ts:393-427` (`convertRemoteVideoToMp4FileInternal`).
- The `catch` after the copy attempt is bare: it cannot tell "this codec needs re-encoding" from "this file was too big to finish in the budget". **A TIMEOUT must not fall through to compress.** `runFfmpeg` rejects with `new Error("Video conversion timed out")` (`:67`) — give that a distinguishable type (e.g. `class FfmpegTimeoutError extends Error`) and rethrow it instead of re-encoding. Only a genuine ffmpeg failure may fall through.
- The copy is a remux whose cost is dominated by pulling the source down, so its budget must scale with the source: `copyTimeoutMs = clamp(DEFAULT_COPY_TIMEOUT_MS, durationSec * 400, 45 * 60 * 1000)`. Duration is already known — `probeRemoteVideo` runs FIRST at `:505-506` and `chooseVideoOptimizationStrategy` at `:193-214`. Thread it through; do not add a second probe.
- Compress stays for the cases that genuinely need it (VP9/Opus webm → H.264/AAC for iOS/Safari, `:196-198`; >1080p / >2.5 Mbps downscale, `:205-211`) but is **skipped when `durationSec > COMPRESS_MAX_DURATION_SEC` (3600)**; log one line saying it was skipped and why. Serving the raw upload is proven safe — `app/api/playlist/route.ts:286-297` HEADs `result.mp4` and redirects to the raw key when absent, and `workflows/process-video.ts:83-86` documents exactly this fallback.
- **Log one outcome line per optimization attempt** — `strategy`, `durationSec`, elapsed ms, and `ok` / `timeout` / `failed`. There is no such record today, which is why nobody knew this pass never succeeds.

## CHANGE 2 — transcription must not queue behind optimization
`workflows/process-video.ts`.
- Today `optimizeAndFinalizeVideo` (`:89`) runs, the `video_uploads` row is deleted (`:43-45`), and only then does `startPendingAiRequest` run (`:50`). Move the AI/transcription start so it no longer waits for optimization. Transcription never needs `result.mp4` — the raw-key fallback is at `workflows/transcribe.ts:782-795`, and the bytes are already verified complete before the workflow starts (`:77-82`).
- The one real orderer is `lib/transcribe.ts`'s upload-in-progress guard, which reads phase `processing` as "bytes still landing". Either start the transcription after the row delete but before optimization, or teach the guard that `processing` means bytes have landed. **Pick the smaller change and say which in the commit message.**
- `startPendingAiRequest` (`:184-194`) selects **without any `deletedAt` filter** — this is why a video deleted at 18:15:55 on prod started processing at 18:24:51. Add the filter.

## CHANGE 3 — cancel on delete, in the loop, not in the per-chunk catch
- New `apps/web/lib/video-alive.ts`: `assertVideoNotDeleted(videoId)` reading `videos.deletedAt`, throwing a **FatalError** (the type `workflows/` already treats as terminal).
- Call it: before remux in `process-video.ts`, and in `workflows/transcribe.ts` **in the chunk loop itself**, NOT inside the per-chunk try/catch at `:1192-1204` — that catch swallows throws and the job only fails when every chunk fails (`:1258`), so an assert placed there is silently defeated. This is the review's finding; get it right.
- A deleted video must stop within roughly one chunk and must never reach COMPLETE.

## One constant is a judgement call, stated honestly
`copyTimeoutMs = clamp(10 min, durationSec * 400, 45 min)` is not derived from a measurement. The copy is a remux whose cost is dominated by pulling the source down, and neither the source file size nor the box's egress bandwidth was measured (two attempts to measure it from outside failed — the speed-test endpoint returned 1 byte, and `/api/playlist?videoId=…` answers 400, so the parameter name is wrong). What makes the imprecision tolerable is CHANGE 2: once transcription no longer waits behind optimization, a copy that takes 40 minutes costs the user nothing — it runs behind a video that is already being transcribed and is already playable. **If the constant is ever tuned, tune it from the outcome line CHANGE 1 adds (elapsed ms per attempt), not from a guess.**

The owner asked for the fix to be proven by an actual upload ("biror videoni qayta yuklab ko'raver ozingiz"). There is no session credential available to this machine, and asking for his password would be the wrong way to get one. 1. A short file would prove nothing, because a short file's optimization has always been fast.
2. Mint a short-lived `sessions` row for the existing admin user, use it to drive the app's own upload API exactly as a browser would, then DELETE the session row. No password is read, entered, or stored; nothing about the account changes.

4. Delete the test video afterwards — which doubles as the live test of cancel-on-delete, since the deletion lands while work is still running.

Cost: one transcription pass over ~65 minutes of tone, roughly $0.30–0.70 of API spend. Recorded here so it is not a surprise on the bill.
